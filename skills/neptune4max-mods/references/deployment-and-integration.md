# 部署细分流程：P1～P4

从[复刻总流程](replication-workflow.md)确定所选模块和授权。以下是实施步骤，专题文档解释参数和接口；不包含任何可直接执行的全机安装命令。

## P1：盘点实际环境与配置

输入：完整仓库、目标地址/连接方式、任务范围。

1. 确认机器是否打印、暂停或执行维护。正在工作时只读取允许的状态和文件，不为检查重启、改加热目标或打断任务。
2. 读取实际服务启动命令、用户、解释器、源码/配置目录、Linux MCU 程序和服务路径。区分终端 Python 与 Klipper/Moonraker 的服务解释器，记录平台、版本、HEAD 和 dirty 文件。
3. 读取主配置、递归 include、SAVE_CONFIG 尾段，以及相关宏/延迟宏。标记已有引脚占用、rename_existing、原厂启动坐标赋值、床网重定向、退出/取消/空闲行为，不默认与参考机一致。
4. 对照所选模块读取目标源文件和接口。ADXL 还需核对实际工具头传感器、轴映射、SPI、Linux MCU 协议；风扇需确认共用输出，双 Z 需确认板型及模块丝印。
5. 汇总“已知 / 需比较 / 需用户测量”的项目。可使用仓库只读 preflight 工具做盘点，但在工具尚未存在于目标机时，不把只读请求当成安装文件或修改服务的授权。

完成：目标基线可定位、能区分现有功能和本次增量；地址/目录/解释器不再靠猜测。

失败处理：连接或权限不足时保留本地分析，向用户索取必要信息；未知版本先比较接口，不能用升级系统或整份覆盖来消除差异。详见[软件环境](../../../docs/software.md#先识别目标机器)。

## P2：选择依赖，准备适配与备份

输入：P1 基线、所选功能、总流程的依赖矩阵。

1. 为每个所选功能列出目标文件、配置 sections、注册命令、物理前提与验收项。标记“已有可复用 / 需新增 / 需最小合并 / 暂不适用”，排除用户未选模块。
2. 在本地隔离目录准备差异：保留原厂 PID、已标定方向、限速、PA、床网和用户宏；参考机电流/坐标/窗口仅作为待核对资料。列出尚缺的侧别、丝杆坐标、探针偏移和擦嘴几何。
3. 处理模块边界：无 ADXL 的双 Z 不载入 PREPARE_WIPE 包装；仅自适应床网要独立适配 resolver；FAN4 电机列表按实际驱动组成调整；检查 M17/M84/退出宏是否正确处理新增 Z 电机。
4. 按授权在任何配置、源码或硬件变更前保存涉及文件、原 Linux MCU 程序/服务定义、权限、所有者和哈希，并下载私有副本。仅方案任务则给备份清单，不写机器。
5. 为每个部署批次写明恢复哪些文件/程序、使用哪个服务以及如何验证恢复。Linux MCU、主机 Python 和 cfg 是配套回退，不能只恢复其中一个。

完成：用户和下一位智能体可看懂将改什么、依赖什么、如何验证和撤回；备份可读取，待标定值没有伪装成已验证。

失败处理：备份或接口比较未完成时不覆盖原文件。保留已完成的准备，不以降低保护、放宽接触边界或恢复历史模板代替适配。

## P3：由用户完成断电硬件装配

输入：所选物料、[装配与照片](../../../docs/hardware.md)、P2 备份；无硬件改动时记录不适用。

1. 让用户确认断电后再插拔驱动、电机、风扇或跳线。按所选模块解释要完成的物理动作，不能把原厂默认登录可用当成硬件已经安装。
2. 双 Z：拆除同步皮带和丝杆顶部同步带轮，确认两侧可独立调节；将并联线分为原 Z/E1 两路，保留正确的线圈配对和压接。确认 MKS TMC2209 V2.0 安装方向、散热、R110 和只短接 UART，其余跳线留空。
3. 风扇：按选择保留主通道、连接独立辅助通道，或将驱动散热接 FAN4；核对电压/极性并保留热端散热。依接线图确认同一路输出，不能靠改名称获得独立控制。
4. 擦嘴：安装 A1 适用硅胶条并检查固定、工具头及热床接线的间隙。收集安装位置和可达范围，照片只能帮助识别，不能替代坐标/接触高度测量。
5. 记录用户确认的模块、跳线、线序和装配状态。允许标记“预计哪侧”，实际驱动侧别和正向仍留待 P6 观察验证；重新上电不代表已归位。

完成：所选硬件具备加载和受控验收条件，缺少的物理条件已明确。

失败处理：用户尚未完成接线/测量时可继续本地源码准备，不执行对应实体功能。模块型号、相线或方向尚不能支持安全归位时先检查装配，不盲目 G28。

## P4：构建、合并与分批加载

输入：经接口比较的差异、备份、所选硬件确认，机器空闲及有效部署授权。

### P4.1：准备所选源码

1. 只为所选功能适配源码。普通双 Z/风扇不因此引入 Tap Linux MCU；metadata 只合并 Bambu/预览接口所需差异；gcode_move.py 仅供参考，不作为默认替换文件。
2. 选择 autotune 时固定仓库所列上游基线，合并 Python 2 除法、反射、旧 TMC 接口兼容；同时提供 motor_constants/数据库依赖，核对真实电机数据。不运行滚动版安装脚本代替比较。
3. FAN4 需要空 heater 列表时检查目标 controller_fan；仅对不支持的版本合并空名称过滤。记录有效加热器列表及既有行为仍保留。
4. 选择中心参考温漂修正时，按[专项D1～D3](adaptive-mesh-drift.md)核对原生床网/probe/实际归位事件接口，安装新Python模块并合并adaptive配置；不修改原生bed_mesh/probe，不引入Tap或MCU改动。
5. 选择 ADXL 时在隔离的完整目标兼容 Klipper 源树合并 Tap C，用 Linux process 配置构建。确认所需依赖后安装最小必要项，检查架构、Tap 命令字典、主机端参数签名和实际服务路径。不能从参考机磁盘原版 C 或仅凭 strings 命中判断构建正确；不顺带刷主板 STM32。详见[构建步骤](../../../docs/software.md#linux-mcu-源码与构建)。
6. 在各模块的实际服务解释器下做不执行硬件动作的语法/兼容检查。源码逻辑有适配变更时运行相关离线回归；仓库测试通过不能替代目标接口或实机验收。

完成：所选源码可解释/可构建，来源和目标接口明确。仓库不分发已验证可直接安装的 MCU 二进制，构建结果需目标机验收。

### P4.2：合并配置与加载顺序

1. 合并所选 sections 并核对重复引脚/宏、include 路径、SAVE_CONFIG 覆盖和命令注册。原 Z 与新增 Z1 共用现有 PA11 归位基准；不得把参考 PA11 offset=0、临时基线=-2 作为独立通用设置照抄。参考 ADXL cfg 还带 default 床网启动加载/触摸屏重定向；目标尚无该 profile 时暂不合并此段，合法测网生成后再按实际需求适配，不能加载不存在的 profile。
2. 双 Z 可先只加载驱动、z_tilt 和 DUAL_Z_LEVEL。完整方案中先注册 ADXL Python 命令及 adaptive 入口，再加载改名 PREPARE_WIPE 的双 Z 包装宏；不能改名尚不存在的命令。参考文件合并后可能需要拆分，不能机械逐个 include。
3. PA11 继续负责 G28/床网/Z_TILT；保留探针及机械基准。ADXL 原始坐标、允许的接触窗口、hard floor、床网覆盖和擦嘴位置明确前，不让完整开始代码可被误当成已验收入口。
4. 按可诊断批次部署、加载和检查：每批只涉及可一起验证的功能及其依赖，记录修改前后哈希、目标位置和恢复方式。确保检测/加载所需配置不会在启动延迟宏中自动执行新运动。
5. 修改已导入 Python 时按实际服务方式重启进程，而非只发 G-code RESTART；Linux MCU 改动按实际服务关系加载配套程序和主机模块。验证进程、命令、日志、配置和 Ready，将真实归位状态重新标为未确认。

完成：所选模块可加载，命令存在，MCU 协议匹配且 Ready；没有将默认坐标或启动床网加载误记为机械验收。

失败处理：先找第一个加载/协议错误，停止相关功能并恢复该批配套文件。服务 active 不等于 Ready；不为验证加载成功而自动加热、归位或碰床。详见[验收与回退](../../../docs/validation.md)。
